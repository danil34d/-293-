## 2) Анализ #1: Логика домена и целостность данных

### Сильные стороны
- Сущности разделены по каталогам `data/*`, структура читаемая.
- Денежные и складские операции в ключевых местах уже связаны с инвалидацией кэшей.
- Добавлена единая функция обновления клиентских балансов.

### Проблемы
- JSON-файлы не дают транзакционность и блокировки при конкурирующих записях.
- Логика частично размазана между API-роутами (риск расхождения правил).
- Есть точечный хардкод контекста пользователя в планировании смен.

### Улучшения
1. Вынести write-операции в сервисный слой (`src/services/*`) с едиными use-case методами.
2. Ввести unit-of-work для связанных операций (мойка -> баланс -> склад).
3. Подготовить миграцию критичных сущностей на SQLite/PostgreSQL.

## 3) Анализ #2: Обработчики API, безопасность, доступы

### Сильные стороны
- Write-обработчики покрыты guards `requireAuth/requireAdmin` (кроме login/logout по смыслу).
- Сессионная cookie укреплена (`httpOnly`, `sameSite`, `secure`).
- Клиентская проверка сессии переведена на серверный endpoint `/api/auth/me`.

### Проблемы
- Ролевая модель бинарная (`admin`/остальные), нет гранулярных прав.
- Нет централизованной валидации payload через схемы (часто только ручные проверки).
- Нет rate limiting для тяжелых/дорогих endpoint (AI/OCR).

### Улучшения
1. Ввести матрицу прав (RBAC) по действиям и разделам.
2. Включить schema-валидацию request/response (zod) для всех write API.
3. Добавить rate limit и audit-log для AI/OCR/admin-операций.

## 4) Анализ #3: Производительность и масштабируемость

### Сильные стороны
- Используются in-memory кэши в `data-loader`.
- Имеются точечные invalidate-функции после изменений.

### Проблемы
- Кэши живут в памяти процесса, нет межпроцессной согласованности.
- Чтение директорий и сериализация JSON масштабируется плохо при росте данных.
- Риск деградации на больших журналах моек/транзакций.

### Улучшения
1. Перейти на хранение с индексами и фильтрацией на уровне БД.
2. Ввести пагинацию/limit по умолчанию на журнальные endpoint.
3. Добавить baseline-метрики (время ответа, размер данных, частота ошибок).

## 5) Анализ #4: Качество, тестирование, эксплуатация

### Сильные стороны
- Есть старт/стоп скрипты для Windows, есть рутинный health-check.
- TypeScript-проверка стабильно проходит.

### Проблемы
- Нет автоматических тестов логики денег/балансов/зарплаты.
- `lint` не активирован (ESLint не инициализирован).
- Документация и фактический статус могут расходиться без регулярной синхронизации.

### Улучшения
1. Поднять минимальный набор тестов:
   - unit: salary, balances, inventory deltas;
   - API smoke: auth, wash-events, invoices, expenses, reset-data.
2. Инициализировать ESLint и включить `typecheck + lint + build` в регулярный прогон.
3. Добавить еженедельный регламент проверки и шаблон отчета.
