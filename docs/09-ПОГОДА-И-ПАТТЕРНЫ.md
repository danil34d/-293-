# Погода и паттерны (рекомендации для планирования смен)

Актуально на: **2026-02-15**

Этот документ описывает:
- как работает “Погодный помощник” в планировании смен;
- какие рекомендации по людям/боксам он строит;
- какие журналы/файлы формируются для анализа и будущих “умных” рекомендаций.

Связанные документы:
- смены и планирование: `доки/08-ГРАФИК-СМЕН-И-ПЛАНИРОВАНИЕ.md`
- шпаргалки: `доки/02-ШПАРГАЛКИ.md`

---

## 1) Модель автомойки (принятая в проекте)

- 1 мойка, **2 бокса**.
- **Бокс 1**: основной.
- **Бокс 2**: резервный (обычно закрыт, но на пике может включаться).
- Смены: **день/ночь**.
- В холодные месяцы часто **ночь отключают** целиком (“ночью топиться невыгодно”).

---

## 2) Где включается в вебе

1. `http://localhost:3000/schedule/planning`
2. Открыть план нужного месяца → “Требования по дням”.
3. Блок “Погодный помощник (Вязники)”.

Важно:
- он работает **для требований**, а не для уже созданных смен.
- после рекомендаций нужно нажать “Автозаполнить” в списке планов (или назначать смены вручную в `/schedule`).

---

## 3) Источник прогноза

Провайдер: **Open‑Meteo** (без API ключа).

Локация зафиксирована в коде:
- `src/services/weather-forecast-service.ts` (`VYAZNIKI_LOCATION`)

API:
- `GET /api/weather/forecast?month=YYYY-MM` (требует `admin`)

Ограничение:
- прогноз даётся только на ближайшие дни (обычно до ~16 дней).
- если даты месяца выходят за окно прогноза, они считаются “без прогноза”.

Кэш:
- файл: `data/_meta/weather-cache/open-meteo_vyazniki.json`
- TTL: 30 минут
- `stale-if-error`: при проблемах сети может использоваться “устаревший” кэш (до 24 часов).

---

## 4) Как строятся рекомендации (дневной поток)

### 4.1 Сильные осадки → 1 сотрудник
Правило:
- дождь `>= 8 мм/сутки` **или** снег `>= 2 см/сутки`

Рекомендация:
- `Бокс 1 День = 1`
- `Бокс 2 День = 0`

### 4.2 Обычный день → 2 сотрудника
Рекомендация по умолчанию:
- `Бокс 1 День = 2`
- `Бокс 2 День = 0`

### 4.3 “Пик после осадков” → 3 сотрудника (2+1)
Эвристика:
- если был день “сильные осадки”,
- и после него есть **3 дня подряд** “солнышко/сухо”,
- то на **первые 3** такие дня рекомендуется “пик”:

Рекомендация:
- `Бокс 1 День = 2`
- `Бокс 2 День = 1`

“Солнышко/хорошая погода” (упрощённая классификация):
- `weatherCode` ∈ {0, 1, 2} (ясно/почти ясно/переменная облачность)
- дождь < 1 мм/сутки
- снег < 0.1 см/сутки

---

## 5) Как применять в UI (чтобы не ломать ручные правки)

Кнопка: **“Заполнить пустые дни”**
- заполняет **только дни**, которых ещё нет в `dailyRequirements`;
- уже настроенные вручную дни не трогает.

Примечание:
- дни без прогноза заполняются как “Норма: 2”.

---

## 6) Быстрые инструменты “открыть/закрыть слоты” на месяц

В “Требования по дням” есть инструменты:
- “Ночные смены отключены в этом месяце”:
  - обнуляет ночные требования;
  - скрывает поля ночи.
- “Бокс 2 отключен в этом месяце (резерв закрыт)”:
  - обнуляет требования по боксу 2;
  - помогает держать модель “бокс 2 по умолчанию 0”.
- “Быстрое открытие/закрытие слота”:
  - выбрать слот (Бокс 1/2 День/Ночь),
  - задать значение 0..2,
  - применить к выбранным дням (галочки).

## 7) Журналы и файлы для анализа (паттерны)

Цель: “собирать факты”, чтобы дальше делать более точные рекомендации (по сезонам/погоде/трафику).

### 7.1 Журнал погодных рекомендаций
Создаётся best-effort при вызове `GET /api/weather/forecast`:
- `data/_meta/pattern-journal/weather-recommendations-YYYY-MM.json`

Содержит:
- окно прогноза,
- классификацию дней,
- рекомендации `1/2/3` и причины (`reason`).

### 7.2 Журнал месяца (мойки + смены + погода)
Endpoint:
- `GET /api/pattern-journal/month?month=YYYY-MM` (требует `admin`)

Файл:
- `data/_meta/pattern-journal/monthly-YYYY-MM.json`

Содержит по каждому дню:
- `washCount`, `revenueTotal`, `paymentBuckets`
- сводку по сменам (сколько людей в слотах боксов/дня/ночи)
- погоду, если день попал в окно прогноза (иначе `null`)

Ограничение:
- для прошлых месяцев погода обычно `null` (нет исторического архива в этой версии).

## 8) Что будет логичным следующим шагом (roadmap)

1. Добавить **историческую погоду** (Open‑Meteo archive) и кластеризацию:
- “погода → сколько моек было”
- “погода+выходные → спрос”
2. Вести “настройки модели” (пороги, локация) в `settings` (через UI), а не в коде.
3. Автоматически предлагать шаблон требований на месяц:
- по паттернам прошлого месяца (уже есть),
- усиленный по погоде + по фактическим мойкам.
