# Журнал: Веб + Telegram как единая система (подробная версия)

## 1. Что это за проект
- Это операционная система автомойки с двумя рабочими каналами:
  - веб-интерфейс (админ + сотрудник);
  - Telegram-бот сотрудника.
- Оба канала работают поверх одного доменного ядра и одного хранилища `data/*`.
- Цель архитектуры: любые операции (мойка, смены, финансы) должны давать одинаковый результат независимо от канала ввода.

## 2. Границы системы и runtime

### 2.1 Технологический контур
- Frontend + API: `Next.js 14` (`src/app`, `src/app/api`).
- Telegram worker: `telegram-bot/worker.mjs` (long polling).
- OCR: Python-скрипт `scripts/plate_reader.py` через сервис `src/services/plate-recognition-service.ts`.
- Опциональный backend: `backend-go` (включается через `USE_GO_BACKEND=true`).

### 2.2 Топология запросов
1. Пользователь веба -> Next pages -> Next API -> `src/services/*` -> `data/*`.
2. Сотрудник в Telegram -> Telegram Cloud -> `telegram-bot/worker.mjs` -> `/api/telegram/internal/*` -> `src/services/*` -> `data/*`.
3. OCR поток:
   - веб: `/api/recognize-plate`;
   - TG: `/api/telegram/internal/recognize-plate`;
   - внутри: вызов Python runtime + EasyOCR.

## 3. Модули веба (функциональная карта)

### 3.1 Основные разделы `src/app/*`
- `dashboard` — сводные KPI и аналитика.
- `employee/workstation` — станция регистрации мойки.
- `wash-log` — журнал моек (просмотр/правка/удаление).
- `employees` — сотрудники, роли, Telegram Chat ID, финкарточки.
- `schedule` — смены, планирование, статусы по дням.
- `counter-agents`, `aggregators` — клиенты B2B/агрегаторы, прайсы, баланс, авто.
- `salary-report`, `salary-schemes` — расчет начислений и схем оплаты.
- `expenses`, `inventory`, `stock-movements` — расходы и склад химии.
- `client-analytics`, `invoices` — балансы и акты.
- `ai-assistant` — AI-контур и фоновые анализы.

### 3.2 Веб API (ключевые группы)
- Auth: `/api/auth/login`, `/api/auth/logout`, `/api/auth/me`.
- Операции автомойки: `/api/wash-events`, `/api/wash-events/[id]`.
- Клиенты: `/api/counter-agents*`, `/api/aggregators*`, `/api/client-transactions/[clientId]`.
- Сотрудники: `/api/employees*`, `/api/employees/[id]/transactions`.
- Финансы и склад: `/api/expenses*`, `/api/inventory*`, `/api/stock-movements`.
- График: `/api/shifts*`, `/api/schedule-plans*`, `/api/employee-day-statuses*`.
- Запросы смен: `/api/shift-assignment-requests*`, `/api/shift-swap-requests*`.

## 4. Telegram-контур (функциональная карта)

### 4.1 Главные сценарии сотрудника
- `/wash` — чатовый мастер регистрации мойки (основной сценарий).
- `/workstation` — выдача одноразовой ссылки в веб-станцию.
- `/today`, `/week`, `/month` — график сотрудника.
- `/requests` — входящие/исходящие заявки + запросы на назначение.
- `/finance` — сводка начислений/выплат за месяц.
- `/help`, `/menu`, `/cancel` — навигация и сброс диалога.

### 4.2 Internal API для бота
- Общие: `/api/telegram/internal/employee-links`, `/schedule`, `/requests`, `/finance-summary`, `/snapshot`.
- Запросы смен:
  - `/api/telegram/internal/shift-assignment/create`
  - `/api/telegram/internal/shift-assignment/cancel`
  - `/api/telegram/internal/shift-swap/create`
  - `/api/telegram/internal/shift-swap/respond`
- Мойка `/wash`:
  - `/api/telegram/internal/wash/bootstrap`
  - `/api/telegram/internal/wash/detect-vehicle`
  - `/api/telegram/internal/wash/services`
  - `/api/telegram/internal/wash/submit`
  - `/api/telegram/internal/recognize-plate`
- WebApp bridge:
  - `/api/telegram/internal/webapp-session/create`
  - `/api/telegram/webapp-login`

## 5. Где хранится бизнес-состояние

### 5.1 Файловая БД `data/*`
- `employees/` — карточки сотрудников.
- `wash-events/` — первичные события мойки.
- `counter-agents/`, `aggregators/` — клиенты и баланс.
- `expenses/` — расходы.
- `inventory.json`, `stock-movements/` — склад и движения химии.
- `shifts/`, `schedule-plans/`, `employee-day-statuses/` — график.
- `shift-assignment-requests/`, `shift-swap-requests/` — заявки.
- `employee-transactions/`, `client-transactions/` — денежные проводки.
- `telegram-bot/` — runtime-state бота (конверсации, snapshot cache, lock-файлы, webapp sessions).

### 5.2 Ключевой принцип
- `data/*` — источник истины.
- UI (веб и TG) не должен напрямую править файлы.
- Запись идет через API и доменные сервисы.

## 6. Общее доменное ядро (что переиспользуется)

### 6.1 Создание мойки
- Сервис: `src/services/wash-event-create-service.ts`.
- Используется и вебом (`POST /api/wash-events`), и Telegram (`/wash/submit` через `wash-registration-service`).
- Эффекты при создании:
  - запись события мойки;
  - списание химии из `inventory`;
  - создание `stock-movements` (consumption);
  - изменение баланса клиента (`sourceId`).

### 6.2 Telegram `/wash` сервис
- Сервис: `src/services/wash-registration-service.ts`.
- Что делает:
  - проверка допуска по смене на сегодня;
  - авто-контекст по номеру (контрагент, агрегатор, прошлые услуги);
  - построение каталога услуг по типу оплаты;
  - расчет total/net/acquiring;
  - submit в единый сервис создания мойки.
- Надежность:
  - идемпотентность по `draftId`;
  - защита от дублей через in-memory map + file lock (`data/telegram-bot/wash-draft-locks`);
  - сохранение результатов draft в `data/telegram-bot/wash-drafts.json`.

### 6.3 Запросы на смены
- Сервисы:
  - `src/services/shift-assignment-service.ts`
  - `src/services/shift-swap-service.ts`
- Один и тот же код обслуживает веб и TG, чтобы не было расхождений правил.

## 7. Сквозные бизнес-потоки (подробно)

### 7.1 Поток А: мойка из веб-станции
1. Сотрудник авторизуется (cookie `employee_auth_sim`).
2. В `/employee/workstation` выбирает оплату/клиента/услуги/команду.
3. UI отправляет `POST /api/wash-events`.
4. API вызывает `createWashEvent`.
5. Сервис пишет `wash-events`, корректирует склад и баланс клиента.
6. Данные сразу видны в `wash-log`, `dashboard`, `client-analytics`.

### 7.2 Поток B: мойка из Telegram `/wash`
1. Сотрудник запускает `/wash`.
2. Worker запрашивает bootstrap и проверяет смену на сегодня.
3. По номеру авто вызывает detect endpoint, получает рекомендации.
4. По оплате получает каталог услуг (с приоритетом прошлой мойки).
5. После подтверждения отправляет `wash/submit`.
6. Дальше работает тот же доменный сервис, что и в вебе.

### 7.3 Поток C: WebApp fallback из Telegram
1. Worker вызывает `/api/telegram/internal/webapp-session/create`.
2. Сервер создает одноразовый токен в `webapp-sessions.json`.
3. Пользователь открывает `/api/telegram/webapp-login?token=...`.
4. Сервер валидирует токен, ставит `employee_auth_sim` и редиректит на `/employee/workstation`.

### 7.4 Поток D: запрос смены из Telegram
1. Сотрудник создает заявку через меню бота.
2. Worker отправляет internal create endpoint.
3. Менеджер подтверждает/отклоняет в вебе.
4. Snapshot/diff сервис отправляет сотруднику уведомление о новом статусе.

## 8. Финансовые и складские инварианты

### 8.1 Деньги
- Баланс клиентов меняется централизованно через `updateClientBalanceById`.
- Для `sourceId` при создании мойки применяется `-totalAmount`.
- При удалении мойки делается обратная операция возврата баланса.
- Изменение цены или источника на `PUT /wash-events/[id]` пересчитывает только разницу.

### 8.2 Химия
- Списание химии при мойке рассчитывается:
  - из услуги (`chemicalConsumption`), если явно задано;
  - иначе по настройкам inventory (auto-deduct, dilution/default).
- Каждое списание фиксируется в `stock-movements`.
- При удалении мойки химия возвращается на склад.

### 8.3 Роли
- Ролевая модель: `EmployeeRole = 'admin' | 'employee'`.
- Основной источник прав: `employee.role`.
- Fallback совместимости: `username === 'admin'` считается admin.

## 9. Безопасность и доступ

### 9.1 Веб
- Сессия: `employee_auth_sim` (httpOnly cookie).
- Guards:
  - `requireAuth()` — защищает приватные операции;
  - `requireAdmin()` — операции менеджера.

### 9.2 Telegram internal API
- Обязательный заголовок: `x-telegram-bot-secret`.
- Проверка в `src/lib/telegram-internal-auth.ts`.
- Без секрета запросы отклоняются (`401`), при незаданном секрете сервис дает `503`.

### 9.3 WebApp session
- Токен криптослучайный, одноразовый.
- TTL управляется `TELEGRAM_WEBAPP_SESSION_TTL_SEC`, диапазон 30..3600 сек, дефолт 120.
- Повторное использование токена запрещено (`usedAt`).

## 10. Эксплуатация и запуск

### 10.1 Скрипты
- `START.ps1`:
  - читает `.env.local`;
  - при `USE_GO_BACKEND=true` поднимает Go;
  - запускает Telegram worker отдельным процессом;
  - запускает Next dev.
- `STOP.ps1`:
  - завершает worker по PID и добивает зависшие процессы;
  - освобождает порты 3000..3005 и 8080.
- `scripts/rebuild-safe.ps1`:
  - stop -> cleanup -> install -> typecheck -> build -> bot dry-check.

### 10.2 Логи (Windows)
- Telegram: `%TEMP%\\carwash_telegram_bot.log`
- Telegram stderr: `%TEMP%\\carwash_telegram_bot.err.log`
- Go backend (если включен): `%TEMP%\\carwash_backend.log`, `%TEMP%\\carwash_backend.err.log`

## 11. Диагностика проблем (практический runbook)

### 11.1 Бот не отвечает
1. Проверить, что запущен worker (`npm run bot:telegram` или `START.ps1`).
2. Проверить `telegram-bot/.env.local` (`TELEGRAM_BOT_ENABLED=true`, токен, base url, secret).
3. Проверить `TELEGRAM_BOT_SECRET` в корневом `.env.local` и совпадение с bot env.
4. Проверить привязку сотрудника (`telegramChatId` в карточке сотрудника или map в env).

### 11.2 `/wash` блокируется
1. Проверить смену сотрудника на сегодняшнюю дату в `shifts`.
2. Проверить, что сотрудник не admin.
3. Проверить internal endpoint `/api/telegram/internal/wash/bootstrap`.

### 11.3 OCR не распознает
1. Проверить Python runtime и зависимости EasyOCR/OpenCV.
2. Учесть, что первый запуск может долго скачивать модели.
3. Проверить читаемость номера на фото (угол, свет, резкость).

## 12. Реальные ограничения текущей версии
- Хранилище JSON без транзакций и row-locking дает риск гонок при высокой параллельности.
- Часть редких/массовых операций удобнее выполнять через веб.
- При локальном `localhost` Telegram может ограничивать URL-кнопки WebApp, поэтому используется fallback ссылкой.

## 13. Контроль качества и регрессии

### 13.1 Минимальный технический чек
1. `npm run typecheck`
2. `npm run build`
3. `TELEGRAM_BOT_ENABLED=false npm run bot:telegram` (graceful exit)

### 13.2 Минимальный функциональный чек
1. Логин admin в веб.
2. Создание мойки из веба.
3. Создание мойки через Telegram `/wash`.
4. Проверка консистентности в `wash-log`, `dashboard`, `client-analytics`.
5. Запрос смены из TG -> подтверждение в веб -> уведомление обратно в TG.

## 14. Вывод техлида
- В проекте уже реализован рабочий омниканальный контур: веб + Telegram не конкурируют, а используют одно доменное ядро.
- Критически важное решение — переиспользование сервисов (`wash-event-create-service`, shift services), что снижает риск расхождений учета.
- Главные точки роста: надежность файловой БД под нагрузкой, автоматизированные регресс-тесты денежных сценариев, дальнейшая стандартизация API-контрактов.
