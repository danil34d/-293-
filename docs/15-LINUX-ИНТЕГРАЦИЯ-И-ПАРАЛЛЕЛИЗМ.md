# Linux интеграция и параллелизм

Дата: 2026-03-11

## Короткий вывод

Для этого проекта правильнее думать не в терминах "многопоточности внутри приложения", а в терминах:

- отдельных процессов
- отдельных systemd-сервисов
- ограниченных фоновых очередей
- разведения интерактивной работы и тяжёлых задач

Node.js и так хорошо справляется с I/O через event loop. Узкие места здесь другие:

- OCR
- фоновые уведомления
- тяжёлые отчёты
- рост числа записей и одновременных действий

## Что уже хорошо интегрировано с Linux

- проект работает как `carwash-web.service`
- Telegram bot вынесен в `carwash-bot.service`
- есть `backup.timer`
- есть `health-check.timer`
- Linux уже перенесён на внутренний диск
- данные уже на `ext4`, а не на `NTFS`

Это уже хорошая база. Следующий уровень — не переписывать всё, а разнести тяжёлые роли по отдельным Linux-процессам.

## Где параллелизм реально нужен

### 1. OCR

Это лучший кандидат на отдельный worker.

Почему:

- OCR CPU-bound
- он не должен висеть внутри HTTP-запроса
- он может тормозить ввод машины и всю рабочую станцию

Практическая схема:

- web кладёт задачу в очередь
- `carwash-ocr-worker.service` забирает задачу
- результат пишется в файл/таблицу/статус задачи
- web клиент опрашивает результат

Для текущего железа:

- concurrency `1`
- максимум `2`, если тест покажет, что CPU не уходит в постоянный 100%

### 2. Telegram и уведомления

Бот уже вынесен отдельно, это правильно.

Но дальше стоит развести:

- интерактивный bot flow
- отправку уведомлений из web-части

Правильнее:

- web пишет событие в очередь
- `carwash-notify-worker.service` отправляет сообщения

Так web не будет ждать Telegram API.

### 3. Отчёты и аналитика

Отчёты не должны исполняться в основном пользовательском запросе.

Нужно выносить отдельно:

- генерацию PDF/DOCX
- тяжёлые аналитические пересчёты
- агрегации для дашборда

Под это нужен:

- `carwash-job-runner.service`

### 4. Backup и maintenance

Это уже вынесено timer'ами, и это правильно.

Дальше можно добавить:

- ночную чистку временных файлов
- архивирование старых OCR-failed
- пересборку агрегатов

## Что не нужно делать сейчас

- не нужен Kubernetes
- не нужна микросервисная архитектура
- не нужен Redis только ради слова "очередь"
- не нужны worker_threads "потому что многопоточность"

На текущем масштабе проще и надёжнее:

- systemd
- отдельные процессы
- файловая очередь или SQLite-таблица задач

## Правильная архитектура на следующем шаге

### Базовый набор сервисов

- `carwash-web.service`
- `carwash-bot.service`
- `carwash-ocr-worker.service`
- `carwash-job-runner.service`
- `carwash-backup.service` + timer
- `carwash-health-check.service` + timer

### Очереди

Минимальный реалистичный вариант:

- файловая очередь в `/srv/carwash/queue`
- подкаталоги:
  - `pending`
  - `processing`
  - `done`
  - `failed`

Или чуть более зрелый вариант:

- SQLite job table

Для текущего масштаба этого достаточно.

## Как ещё сильнее интегрировать проект под Linux

### 1. Жёстче оформить systemd-сервисы

Для web/bot/worker добавить:

- `Restart=always`
- `RestartSec=...`
- `MemoryMax=...`
- `CPUQuota=...` для OCR worker
- `Nice=...`
- `IOSchedulingClass=...`

Это даст предсказуемое поведение под нагрузкой.

### 2. Добавить systemd hardening

Минимум:

- `NoNewPrivileges=true`
- `PrivateTmp=true`
- `ProtectSystem=strict`
- `ProtectHome=true`
- `ReadWritePaths=/srv/carwash ...`
- `RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6`

Это особенно полезно для worker'ов и bot-процессов.

### 3. Развести каталоги по linux-ролям

Нормальная структура:

- `/srv/carwash/app`
- `/srv/carwash/data`
- `/srv/carwash/backups`
- `/srv/carwash/queue`
- `/srv/carwash/runtime`
- `/srv/carwash/logs`

И дальше заводить это через:

- `tmpfiles.d`
- systemd units

### 4. Свести Linux-операционку к воспроизводимому deploy

Идеальное состояние:

- все unit-файлы шаблонизированы в repo
- все рабочие каталоги создаются скриптами
- все права и владельцы назначаются автоматически
- однотипные машины можно поднять повторно без ручной магии

### 5. Ввести event log

Нужен единый журнал событий системы:

- мойка завершена
- OCR ошибка
- сервис перезапущен
- backup завершён
- сотрудник сделал действие

Это пригодится и для wallboard, и для аудита, и для роста до нескольких моек.

## Что заложить под несколько моек

### siteId

Это надо предусмотреть заранее.

Добавить поле `siteId` в:

- wash events
- shifts
- employees
- stock movements
- requests

Даже если сейчас мойка одна.

### Разделение operational и analytical нагрузки

Когда данных станет больше:

- оперативная запись не должна ждать отчёты
- дашборды должны читать из агрегатов
- генерация документов должна идти фоном

## Приоритеты

### Сначала

1. OCR worker
2. Notification / job worker
3. systemd hardening
4. event log

### Потом

1. `siteId`
2. SQLite/SQL job layer
3. переход от JSON к PostgreSQL там, где это уже реально давит

## Практический вывод

Если усилять проект под Linux правильно, то следующий рост должен идти так:

1. не добавлять "потоки" в Node.js ради идеи
2. выносить тяжёлые куски в отдельные Linux service/worker процессы
3. усиливать systemd, limits, hardening и очереди
4. готовить модель данных к нескольким мойкам

Это даст больше стабильности и пользы, чем попытка искусственно сделать "многопоточный монолит".
