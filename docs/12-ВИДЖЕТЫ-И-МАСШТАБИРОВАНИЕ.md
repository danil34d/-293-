## Статус реализации

### Уже сделано

Wallboard реализован и работает на живом сервере.

Системный блок (`/api/wallboard` + `/wallboard`):

- статус сервисов: web, bot, backup timer, health-check timer
- hostname, IPv4, root source, EFI source
- uptime, CPU load, CPU temperature
- RAM (used/total)
- диски: корень, данные, backup (used/available/percent)
- OCR engine (openvino/auto)
- возраст последнего бэкапа

Бизнес-блок:

- моек сегодня, выручка, средний чек
- активные сотрудники и боксы на смене
- ожидающие заявки (swap + assignment)
- нераспознанные номера (OCR failed count)
- последняя машина, лидер смены
- остаток химии на складе (кг)

Клиент обновляется каждые 30 секунд, показывает живые часы, дату и статус обновления.

### Решено ранее

- NTFS как хранилище данных — мигрировано на ext4 (`/dev/sda5` → `/srv/carwash`, `/dev/sda6` → backups). Больше не является узким местом.
- Загрузка с USB — система перенесена на внутренний диск `/dev/sda3` (CARWASH_ROOT). USB остаётся аварийным носителем.

## Что нужно добавить в wallboard

### 1. Лента событий (приоритет: высокий)

Внизу wallboard — короткий хронологический список последних событий за 1–2 часа.

Типы событий:

- мойка завершена (номер, сумма, сотрудник)
- номер не распознан (OCR failed)
- backup завершён
- сервис перезапущен health-check'ом
- смена началась/закончилась

Это самая полезная доработка для оператора. Цифры показывают состояние, а лента показывает что конкретно происходит.

Реализация: собрать последние wash-events, OCR-ошибки, backup-timestamp и systemd-журнал в один массив, отсортировать по времени, ограничить 15–20 записями.

### 2. Пороговая цветовая индикация (приоритет: высокий)

Сейчас цвет есть только у статусов сервисов. Нужно добавить пороги для остальных метрик:

- Диски: >80% = жёлтый, >90% = красный
- RAM: >80% = жёлтый, >90% = красный
- CPU load: >70% = жёлтый, >90% = красный
- Температура CPU: >70°C = жёлтый, >85°C = красный
- Возраст backup: >26 часов = жёлтый, >48 часов = красный
- OCR failed: >5 = жёлтый, >15 = красный
- Химия: <5 кг = жёлтый, <2 кг = красный

Принцип: проблема должна читаться за 1 секунду. Плитка становится контрастной без мигания.

### 3. Мини-графики (приоритет: средний)

Sparkline-графики за последние 24 часа для ключевых метрик:

- количество моек по часам
- выручка по часам
- CPU load

Это даёт контекст — не просто "5 моек", а "5 моек и растём" или "5 моек и спад".

## Дизайн-направление

Основа: функциональный минимализм. Рабочая панель оператора, не маркетинговый лендинг.

Принципы:

- жёсткая иерархия информации
- минимум декоративного шума
- крупная типографика и сильный контраст
- один акцентный цвет на состояние: зелёный = OK, жёлтый = warning, красный = problem
- цифры с табличной шириной (font-variant-numeric: tabular-nums)
- анимация только на смену состояния

Компоновка:

- верхняя строка: hostname, IP, время, дата, статус обновления
- левая колонка: система Linux (CPU, RAM, температура, uptime, сервисы, диски)
- правая колонка: бизнес (мойки, выручка, смена, OCR, химия, сводка)
- нижняя зона: лента событий (ещё не реализована)

## Масштабирование

### Что реально нужно сейчас

**OCR worker** — сейчас OCR вызывается синхронно в HTTP-запросе. Если распознавание зависнет или будет медленным, зависнет весь запрос. Решение:

- отдельный процесс-worker для OCR
- файловая очередь: HTTP-запрос кладёт задачу в папку, worker подхватывает
- ограничение параллелизма (1–2 задачи одновременно на Celeron)
- retry policy: 3 попытки с паузой

Это можно сделать без Redis и без PostgreSQL — достаточно файловой очереди с lock-файлами.

**Telegram уведомления** — отправка не должна блокировать HTTP. Уже частично решено (бот в отдельном процессе), но уведомления из web-части идут синхронно.

### Что заложить на будущее

**siteId** — если появится вторая мойка, нужен идентификатор площадки. Можно добавить необязательное поле `siteId` в wash-events, employees, shifts уже сейчас (стоит ноль усилий, упрощает миграцию потом).

**PostgreSQL** — правильное направление для роста, но переходить стоит только когда JSON-файлы начнут реально тормозить (тысячи wash-events, конкурентная запись, сложные выборки). На текущих объёмах ext4 + JSON справляется.

**Очередь задач** — единый job layer для OCR, отчётов, уведомлений, backup. Минимальная реализация: таблица задач (или папка с JSON-файлами), отдельный worker-процесс, retry с dead-letter.

**Read/write разделение** — при росте тяжёлые отчёты и аналитика не должны мешать операционным записям. Агрегаты считаются отдельно, дашборды читают из готовых снапшотов.

### Что НЕ нужно сейчас

- Kubernetes, Docker Compose для одной мойки на Celeron — overhead без пользы
- Микросервисная архитектура — монолит Next.js достаточен для текущего масштаба
- NVIDIA GPU для OCR — OpenVINO на Intel достаточен
- Многопоточность ради многопоточности — Node.js event loop справляется

## Деплой

Для выкатки кода из GitHub на живой сервер создан скрипт `ops/linux/deploy-from-repo.sh`:

- подтягивает `git pull` в `/srv/carwash/repo`
- синхронизирует код rsync в `/srv/carwash/app` (data, .env.local, node_modules не затрагиваются)
- делает бэкап текущего app перед деплоем
- запускает npm install (если package.json изменился) и npm run build
- при ошибке сборки откатывает на бэкап
- перезапускает carwash-web и carwash-bot
- записывает версию в `.deploy-history`
