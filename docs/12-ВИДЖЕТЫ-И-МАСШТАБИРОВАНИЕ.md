# Виджеты И Масштабирование

Дата: 11.03.2026

## Цель

Нужны два слоя наблюдения:

- системный виджет на экране Linux
- бизнес-виджет по автомойке

И параллельно нужно заложить архитектуру под несколько моек, клиентов, сотрудников и высокую фоновую нагрузку.

## Дизайн-направление

Основа:

- функциональный минимализм
- жёсткая иерархия информации
- минимум декоративного шума
- крупная типографика и сильный контраст
- один акцентный цвет на состояние, а не на украшение

Практический стиль для этого проекта:

- фон: почти белый или графитовый, без градиентного мусора
- сетка: прямые блоки, ровные поля, один ритм отступов
- акцент:
  - зелёный только для `OK`
  - жёлтый только для `warning`
  - красный только для `problem`
- шрифт:
  - читаемый гротеск без декоративности
  - цифры с хорошей табличной шириной
- анимация:
  - только смена состояния, без лишних микроэффектов

Это должно выглядеть как рабочая панель оператора, а не как маркетинговый лендинг.

## Виджет 1. Система

Рабочее имя: `System Pulse`

Что показывать:

- статус `WEB`, `BOT`, `BACKUP`, `HEALTH`
- IP машины
- аптайм
- CPU
- RAM
- свободное место:
  - `ROOT`
  - `CARWASH_DATA`
  - `CARWASH_BACKUP`
- температура CPU и диска
- возраст последнего бэкапа
- OCR engine:
  - `OPENVINO`
  - или `CPU fallback`

Как компоновать:

- верхняя строка:
  - имя машины
  - IP
  - текущее время
- центральный блок:
  - 4 крупных статусных плитки сервисов
- нижний блок:
  - ресурсы системы в виде компактных полос
- правый узкий столбец:
  - температура
  - последний backup
  - версия OCR engine

Что важно:

- проблема должна читаться за 1 секунду
- цифры должны быть стабильны по ширине
- при ошибке плитка становится жёстко контрастной, без мигания

## Виджет 2. Автомойка

Рабочее имя: `Carwash Command`

Что показывать:

- моек сегодня
- выручка сегодня
- средний чек
- активные сотрудники на смене
- очередь или машины в работе
- последние нераспознанные номера
- статус Telegram-бота
- статус OCR
- число критичных ошибок за день
- последнее обновление данных

Как компоновать:

- первая линия:
  - `Моек сегодня`
  - `Выручка`
  - `Средний чек`
- вторая линия:
  - `На смене`
  - `В работе`
  - `Ожидают`
- правая колонка:
  - `OCR`
  - `Bot`
  - `Ошибки`
  - `Backup age`
- нижняя зона:
  - короткий список последних событий
  - например:
  - номер не распознан
  - бот переподключён
  - backup завершён

Принцип:

- верхние цифры отвечают на вопрос бизнеса
- нижние события отвечают на вопрос оператора

## Где это лучше жить

### На рабочем столе Linux

Системный виджет лучше делать как отдельное локальное приложение или kiosk-панель.

Подход:

- маленький локальный веб-интерфейс
- запуск при входе в XFCE
- fullscreen не нужен
- всегда поверх не нужен
- режим: закреплённая компактная панель

Почему не чистый `conky` как основной вариант:

- быстро сделать можно
- но сложно красиво развивать
- сложнее использовать типографику и бизнес-композицию

Лучший путь:

- отдельная `/status` или `/wallboard` страница в проекте
- локальное автооткрытие в браузере или в webview

## Архитектурный вывод по многопоточности

Слово `многопоточность` для этого проекта лучше заменить на три реальных механизма:

- многопроцессность
- очереди фоновых задач
- многосайтовость

Для Node/Next основной выигрыш даст не `threads` ради самих threads, а разделение нагрузки.

## Где реально пригодится параллелизм

### OCR

- распознавание номеров
- повторные попытки на плохих кадрах
- пакетная обработка накопившихся изображений

Здесь уместно:

- отдельный OCR worker
- очередь задач
- ограничение параллелизма по CPU/GPU

### Telegram

- отправка уведомлений
- повторная доставка
- фоновые напоминания

Это не должно блокировать HTTP-запросы.

### Отчёты и аналитика

- зарплатные отчёты
- месячные сводки
- выгрузки
- клиентская аналитика

Это тоже надо выносить в фон.

### Backup и обслуживание

- backup
- очистка старых архивов
- health-check
- пересчёт агрегатов

Это отдельные фоновые job-цепочки.

## Что нужно заложить под несколько моек

### 1. Явная сущность площадки

Нужны ключи:

- `tenantId`
- `siteId`

Их надо провести через:

- мойки
- сотрудников
- расписание
- кассу
- склады
- OCR
- Telegram-привязки
- отчёты

### 2. Изоляция данных

Сейчас файловая модель годится для одной мойки, но для роста это слабое место.

Для многосайтовости лучше целиться в SQL-хранилище:

- PostgreSQL
- строгие индексы
- транзакции
- row-level фильтрация по `tenantId/siteId`

### 3. Очереди задач

Нужен единый job layer:

- OCR jobs
- report jobs
- notification jobs
- reconciliation jobs

Минимум:

- таблица job-очереди в БД
- отдельный worker-процесс
- retry policy
- dead-letter статус

### 4. Разделение read/write нагрузки

При росте моек тяжёлые расчёты не должны мешать операционным записям.

Полезный принцип:

- запись событий отдельно
- агрегаты отдельно
- дешёвые read-model для дашбордов отдельно

### 5. Идемпотентность

Все фоновые задачи должны переживать повторный запуск.

Особенно:

- Telegram отправка
- OCR обработка
- backup
- расчёт зарплаты

## Что делать по шагам

### Ближайший этап

1. Сделать `wallboard` страницу в проекте.
2. На ней собрать:
   - system block
   - carwash block
3. Данные брать из одного агрегирующего `/api/system-overview`.

### Следующий этап

1. Ввести `siteId` в доменную модель.
2. Вынести тяжёлые операции в background jobs.
3. Подготовить переход с JSON на SQL-модель.

### Потом

1. Отдельный OCR worker.
2. Отдельный notification worker.
3. Нормальный event log по системе.

## Главное решение

Если смотреть как backend и как продукт:

- сначала делаем единый wallboard
- затем вводим `siteId`
- затем выносим OCR/отчёты/уведомления в очередь

Именно это даст:

- быстрее интерфейс
- стабильнее система
- готовность к новым мойкам без хаоса
