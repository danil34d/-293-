## 2026-04-26 (вечер) — данные адаптера, reset-data и двойной счёт химии

### Цель
Закрыть несколько несвязанных, но обнаруженных в одну сессию проблем целостности данных, выплывших после того как salary-report наконец начал читать живой Postgres вместо застывшего JSON-кеша.

### Выполнено

1. data-loader runtime-делегирует в pg-adapter.
- В `src/lib/data/index.ts` исходно стоял `const usePostgres = process.env.DATA_SOURCE === 'postgres'` — выполнялся при загрузке модуля. Next.js загружает `.env` после первой top-level evaluation, поэтому при ранней загрузке адаптер навсегда фиксировался на JSON.
- Чтобы избежать переброски всех клиентских импортов на новый путь (это бы поломало стабильные ID серверных экшенов), решение лежит внутри `src/lib/data-loader.ts`: каждая ключевая функция (`getWashEventsData`, `getEmployeesData`, `getSalarySchemesData`, `getAllEmployeeTransactions`, `getViolationsData`, `getAllFinanceDataForEmployee`, `getRetailPriceConfig`, `getAggregatorsData`, `getCounterAgentsData`, `getActiveCounterAgentsData`, `getExpensesData`) теперь выполняет `pgIfPostgres()` на каждом вызове и при `DATA_SOURCE=postgres` форвардит вызов в `./data/pg-adapter`.
- Прод-сборка теперь должна запускаться как `DATA_SOURCE=postgres npm run build` — иначе билд линкуется со «старой» формой адаптера и SSR-страницы могут получить устаревшие 503 от Server Action runtime.

2. /api/reset-data научился чистить Postgres.
- Кнопка «Очистить все финансовые данные» на `/settings` ранее удаляла только JSON-файлы. С учётом того что чтения теперь идут из PG, кнопка тихо ничего не меняла для пользователя.
- В `POST /api/reset-data` добавлен ранний bail-out на `DATA_SOURCE=postgres`: вызывается готовый `resetFinancialData()` из `pg-adapter` (одна транзакция: `WashEventEmployee`, `WashEvent`, `EmployeeTransaction`, `ClientTransaction`, `Expense`, `StockMovement` + обнуление `Aggregator.balance`, `CounterAgent.balance`, `inventory.chemicalStockGrams`).
- После транзакции дополнительно сбрасываются in-memory кеши `data-loader` (`invalidateWashEventsCache`, `invalidateAllEmployeeTransactionsCache`, `invalidateAllClientTransactionsCache`, `invalidateExpensesCache`, `invalidateStockMovementsCache`, `invalidateAggregatorsCache`, `invalidateCounterAgentsCache`, `invalidateInventoryCache`).
- JSON-ветка осталась как fallback для `DATA_SOURCE=json`.

3. Двойной учёт закупки химии в `/api/expenses`.
- Кнопка «Закупка химии» на `/inventory` (`handlePurchaseChemical`) делает два параллельных запроса: `POST /api/stock-movements` (правильный путь учёта изменений склада) и `POST /api/expenses` (для регистрации расхода в журнале трат).
- В `/api/expenses` была пасхалка: при `category === 'Закупка химии'` и `unit ≈ 'кг'` маршрут вызывал `updateInventory(quantity * 1000)` — то есть второй раз бампал `inventory.chemicalStockGrams`. Каждая закупка засчитывалась дважды.
- Поймано в тестовом прогоне: купили 21 кг, ожидали 21000 г на складе, в БД получили 42000 г, после 10 моек по 700 г осталось 35000 г вместо корректных 14000 г.
- В маршруте удалена функция `updateInventory` и весь побочный эффект. Файл теперь только сохраняет `Expense`. Вся бухгалтерия по складу идёт ровно через `/api/stock-movements`.

4. Кнопка `/salary-report` показывала переплату.
- Из-за того что чтения наконец стали приходить из PG, в одной из карточек (Костылев Валерий) обнаружилось что выплата 2960.82 руб. от 26.04 12:01 была сделана под старый, кешированный JSON-расчёт (он показывал начисление 4655.02), тогда как актуальный PG даёт начисление всего 990 руб. за апрель — то есть переплачено 2173.32 руб.
- Решение по этой переплате (вернуть транзакцию полностью, разбить на `payment 787.5` + `loan 2173.32`, или оставить как аванс под май) оставлено за владельцем — соответствующая запись лежит в `memory/session_state_2026-04-26.md`.
