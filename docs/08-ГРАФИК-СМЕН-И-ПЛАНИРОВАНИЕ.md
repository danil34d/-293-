Актуально на: **2026-02-15**

Этот документ нужен, чтобы:
- быстро понять, как устроены **смены** (ручные) и **планирование** (авто-распределение);
- знать **где лежит код** и **какие API/файлы данных** задействованы;
- понимать, как Telegram-бот читает/создает заявки и как приходят уведомления;
- иметь “операционку” для реальных ситуаций (“я вышел на работу, меня нет в графике”).

## 1) Назначение

**Смена** в системе — это назначение 1–2 сотрудников на конкретный:
- день (`date` в формате `YYYY-MM-DD`),
- бокс (`boxNumber`: `1` или `2`),
- тип смены (`shiftType`: `day` или `night`).

В проекте есть 2 связанных, но разных “инструмента”:
1. **График смен** (`/schedule`) — ручное управление сменами + обработка заявок сотрудников (swap/assignment).
2. **Планирование смен** (`/schedule/planning`) — создание “плана” на месяц, настройка статусов дней и потребности по дням, запуск **автозаполнения** (создание смен на месяц автоматически).

Telegram в этой части:
- **читает** смены сотрудника (`/today`, `/week`, `/month`);
- позволяет сотруднику создать **заявку на назначение** (`➕ Запрос смены`) и **заявки на обмен/передачу** (`📨 Заявки`);
- отправляет **уведомления** о сменах/заявках через `snapshot/diff`.

Также смены критично связаны с Telegram `/wash`: если у сотрудника **нет смены на сегодня**, `/wash` блокируется (проверка в `src/services/wash-registration-service.ts`).

- Команды графика: `/today`, `/week`, `/month`

## 3) Модель данных (сущности и инварианты)

Типы находятся в `src/types/index.ts`.

### 3.1 Shift (смена)
Файл типизации: `src/types/index.ts` (интерфейс `Shift`).

Ключевые поля:
- `id: string`
- `date: string` — **`YYYY-MM-DD`**
- `boxNumber: 1 | 2`
- `employeeIds: string[]` — в доменной модели ожидается **1..2**
- `shiftType: 'day' | 'night'`
- `startTime: string` — обычно `08:00` или `20:00`
- `endTime: string` — обычно `20:00` или `08:00`
- `releasedEmployeeId?: string` — “напарника отпустили”, но он остается в `employeeIds` (важно понимать смысл)
- `isAutoAssigned?: boolean` — признак, что смена создана автозаполнением

**Инварианты (что “должно быть”):**
- “слот смены” определяется как `(date, boxNumber, shiftType)`;
- в одном слоте обычно максимум 2 человека;
- сотрудник не должен быть назначен сразу на два слота в один день (это **желательно**, но сейчас не везде валидируется).

### 3.2 ShiftAssignmentRequest (запрос “поставьте меня в смену”)
Файл типизации: `src/types/index.ts` (интерфейс `ShiftAssignmentRequest`).

Поля:
- `employeeId`, `date`, `shiftType`, `boxNumber`
- `status: 'pending' | 'accepted' | 'rejected' | 'cancelled'`
- `resolvedBy`, `resolvedAt` — заполняются при решении менеджером

### 3.3 ShiftSwapRequest (обмен/передача смен)
Файл типизации: `src/types/index.ts` (интерфейс `ShiftSwapRequest`).

Поля:
- `type: 'giveaway' | 'swap'`
- `requesterShiftId` — смена инициатора
- `targetEmployeeId`, `targetShiftId?`
- `status: pending/accepted/rejected/cancelled`

### 3.4 EmployeeDayStatusEntry (статус дня сотрудника)
Файл типизации: `src/types/index.ts` (интерфейс `EmployeeDayStatusEntry`).

Статусы (`EmployeeDayStatus`):
- `free` — “свободен”
- `doesnt_want` — “не хочет работать”
- `vacation_sick` — отпуск/больничный
- `must_work` — “обязательно работать”
- `auto_assigned` — “авто назначен” (в текущей логике почти не используется)

Важно:
- в типе есть `shiftType?/boxNumber?` для `must_work`, но текущий UI **их не задает**, а авто-fill **не использует** это принуждение.

### 3.5 SchedulePlan (план на месяц)
Файл типизации: `src/types/index.ts` (интерфейс `SchedulePlan`).

Поля:
- `month: "YYYY-MM"`
- `employeeConfigs`: настройки нагрузки по сотрудникам
- `dailyRequirements`: требования по дням (потребность)
  - ключевое для авто-fill: `box1DayRequired`, `box1NightRequired`, `box2DayRequired`, `box2NightRequired`
  - `requiredCount` сейчас используется как “флаг пропуска дня”, но **не заменяет** per-box поля
- `isActive` — флаг активного плана для месяца (сейчас это скорее метка, авто-fill можно запускать и с неактивного)

## 4) Файловая БД: где хранится и кто пишет/читает

Данные живут в `data/*` (по сущности отдельные JSON-файлы).

| Сущность | Где хранится | Кто пишет | Кто читает | Код (чтение) | Код (запись) |
|---|---|---|---|---|---|
| Смены (`Shift`) | `data/shifts/*.json` | менеджер через веб; сервисы заявок; авто-fill | веб `/schedule`, `/employee/schedule`, TG `/today` | `src/lib/data-loader.ts#getShiftsData` | `src/app/api/shifts/*`, `src/app/api/schedule-plans/[id]/auto-fill/route.ts`, `src/services/shift-assignment-service.ts`, `src/services/shift-swap-service.ts` |
| План (`SchedulePlan`) | `data/schedule-plans/*.json` | менеджер | менеджер UI | `src/lib/data-loader.ts#getSchedulePlansData` | `src/app/api/schedule-plans/*` |
| Статусы дней (`EmployeeDayStatusEntry`) | `data/employee-day-statuses/*.json` | менеджер | авто-fill, UI редактора планов | `src/lib/data-loader.ts#getEmployeeDayStatusesData` | `src/app/api/employee-day-statuses/*` |
| Запросы назначений | `data/shift-assignment-requests/*.json` | сотрудник (web/TG), менеджер | веб `/schedule`, сотрудник `/employee/schedule`, TG `/requests` | `src/lib/data-loader.ts#getShiftAssignmentRequestsData` | `src/services/shift-assignment-service.ts` (+ API роуты) |
| Запросы swap/giveaway | `data/shift-swap-requests/*.json` | сотрудник (web/TG), менеджер | веб `/schedule`, сотрудник `/employee/schedule`, TG `/requests` | `src/lib/data-loader.ts#getShiftSwapRequestsData` | `src/services/shift-swap-service.ts` (+ API роуты) |
| Telegram snapshot cache | `data/telegram-bot/snapshot-cache/*.json` | internal API (server) | TG worker | — | `src/app/api/telegram/internal/snapshot/route.ts` |

### Права доступа (важно)
- Веб “запись смен/планов/статусов дней” защищена `requireAdmin()` (cookie `employee_auth_sim`).
- Запросы (`shift-*-requests`) создаются через `requireAuth()` (доступны сотруднику), а принятие/отклонение — через сервисы, которые требуют admin.
- Telegram internal API защищены заголовком `x-telegram-bot-secret` (`src/lib/telegram-internal-auth.ts`).

Отдельно: многие `GET /api/*` в проекте открыты без авторизации (это удобно для разработки, но может быть риском в проде).

## 5) Веб: “График смен” (менеджер) — как работает

### 5.1 Где лежит код
- Страница: `src/app/schedule/page.tsx`
- Компонент: `src/app/schedule/components/ScheduleCalendar.tsx`
- Стили печати: `src/styles/schedule-print.css`

`src/app/schedule/page.tsx` (server component) загружает данные:
- `getShiftsData()`
- `getEmployeesData()`
- `getShiftSwapRequestsData()`
- `getShiftAssignmentRequestsData()`

И передает их как `initialShifts/employees/pendingRequests/assignmentRequests` в `ScheduleCalendar`.

### 5.2 Что делает ScheduleCalendar
Компонент строит календарь месяца:
- вычисляет `daysInMonth` через `date-fns`;
- в таблице:
  - строки = сотрудники,
  - столбцы = дни месяца,
  - в ячейке рисуются смены сотрудника на дату (может быть несколько смен на день, если в данных есть дубли/конфликты).

Вверху есть действия:
- **Планирование смен** (переход на `/schedule/planning`)
- **Скачать Excel** (экспорт через `xlsx`)
- **Печать** (через CSS `@media print`)
- **Заявки на обмен** (если есть pending swap)
- **Запросы на смены** (если есть pending assignment)
- **Вызов на помощь** (список “свободных сегодня” сотрудников)

### 5.3 Ручное назначение/редактирование смены (клик по ячейке)
Поток:
1. Клик по ячейке даты/сотрудника → `handleOpenDialog(date, employeeId, existingShift?)`.
2. Если есть смена на эту дату (для сотрудника), UI открывает режим редактирования.
3. Менеджер выбирает:
   - тип смены (день/ночь),
   - бокс (1/2),
   - сотрудников (максимум 2).
4. Нажимает “Сохранить” → `handleSaveShift()`.

UI-валидации (важно понимать ограничения):
- **Конфликт**: UI запрещает назначить сотрудника, если он уже есть в другой смене **того же `shiftType`** на эту дату.
  - Это означает, что вручную можно (случайно) назначить сотрудника на `day` и `night` в один день (UI это не поймает).
- **Лимит бокса**: UI ищет существующую смену `(date, boxNumber, shiftType)` и запрещает превысить 2 человека суммарно.

API-вызов:
- создание: `POST /api/shifts`
- редактирование: `PUT /api/shifts/<id>`
- удаление: `DELETE /api/shifts/<id>`

Серверные факты:
- `POST/PUT/DELETE /api/shifts*` требуют `requireAdmin()` (`src/app/api/shifts/*`).
- API **не валидирует** уникальность слота `(date, boxNumber, shiftType)` и не проверяет ссылки на реальных сотрудников.

### 5.4 “Вызов на помощь”
`ScheduleCalendar` показывает список сотрудников, у кого **нет смены сегодня**, вычисляя:
- все `shifts` на сегодня → `assignedIds` → “свободные” = `employees` минус `assignedIds`.

Важно: если сотрудник “отпущен” (`releasedEmployeeId`), он все равно в `employeeIds`, значит **не попадет** в “свободных”.

### 5.5 Обработка заявок (swap + assignment) в календаре

#### Swap requests (обмен/передача)
- UI: “Заявки на обмен”
- действие менеджера: “Одобрить/Отклонить”
- запрос: `PUT /api/shift-swap-requests/<id>` с `{ status: accepted|rejected, managerApproved }`

Факт: `managerApproved` сейчас сервером не используется (лишнее поле; сервер смотрит только на `status`).

#### Assignment requests (запросы на назначение)
- UI: “Запросы на смены”
- действие менеджера: “Назначить/Отклонить”
- запрос: `PUT /api/shift-assignment-requests/<id>` с `{ status: accepted|rejected }`

При `accepted` используется сервис `src/services/shift-assignment-service.ts`:
- если смена `(date, boxNumber, shiftType)` уже есть и в ней < 2 сотрудников → добавляет сотрудника;
- иначе создает новую смену.

Ограничение: при принятии не проверяется, что сотрудник уже назначен на другую смену в этот день (возможна двойная занятость).

## 6) Веб: “Мой график” (сотрудник) — как работает

### 6.1 Где лежит код
- Страница: `src/app/employee/schedule/page.tsx`
- UI: `src/app/employee/schedule/components/EmployeeScheduleClient.tsx`
- Предпочтения: `src/app/employee/schedule/components/EmployeePreferences.tsx`

`src/app/employee/schedule/page.tsx` достает cookie `employee_auth_sim`, парсит `id`, находит сотрудника в `employees` и отдает в клиент.

### 6.2 Что умеет сотрудник в UI

UI построен вокруг 4 основных сценариев:
1. Посмотреть свои смены (месяц).
2. Запросить смену у менеджера (assignment request).
3. Передать/обменять смену (swap/giveaway request).
4. Отпустить напарника (если смена на двоих) и настроить предпочтения (для планирования).

#### 6.2.1 Просмотр своих смен
Список “Мои смены в месяце” строится из `localShifts` (локальный state) и фильтруется по:
- `shift.date` начинается с `yyyy-MM`;
- `shift.employeeIds` содержит `currentEmployeeId`.

#### 6.2.2 Запросить смену (assignment)
Кнопка: “Запросить смену”.

Что делает:
- открывает диалог;
- выбирается `date`, `shiftType`, `boxNumber`, опциональный `comment`;
- отправляет `POST /api/shift-assignment-requests`.

Серверная логика:
- route: `src/app/api/shift-assignment-requests/route.ts` (`requireAuth()`),
- сервис: `src/services/shift-assignment-service.ts#createAssignmentRequest`,
  - проверяет формат даты `YYYY-MM-DD`;
  - запрещает прошедшие даты;
  - защищает от дубля pending-запроса (409).

Отмена запроса:
- `PUT /api/shift-assignment-requests/<id>` с `{ status: "cancelled" }`.
  - разрешено админу и самому сотруднику.

#### 6.2.3 Передача/обмен смен (swap/giveaway)
Кнопка: “Обмен” (в списке смен).

Что делает:
- создает заявку:
  - `type="giveaway"` (передача смены),
  - `type="swap"` (обмен двумя сменами),
- отправляет `POST /api/shift-swap-requests`.

Серверная логика:
- route: `src/app/api/shift-swap-requests/route.ts` (`requireAuth()`),
- сервис: `src/services/shift-swap-service.ts#createSwapRequest`,
  - инициатор должен быть внутри `requesterShiftId` (иначе 400),
  - для `swap` требуется `targetShiftId` и проверка, что targetEmployeeId состоит в targetShiftId.

Ответ на входящую заявку:
- `PUT /api/shift-swap-requests/<id>` с `{ status: "accepted"|"rejected" }`.
  - разрешено админу или сотруднику-адресату (`targetEmployeeId`).

Ограничение: флаг `employee.canSwapShifts=false` сейчас проверяется UI, но сервером не принудительно ограничен (можно обойти вызовом API напрямую).

#### 6.2.4 “Отпустить напарника” и предпочтения
В UI есть действие “Отпустить” (когда на смене 2 сотрудника) — оно делает:
- `PUT /api/shifts/<shiftId>` с `releasedEmployeeId`.

Также есть карточка предпочтений сотрудника (`EmployeePreferences`) — делает:
- `PUT /api/employee/preferences` с полями:
  - `preferredShiftType`,
  - `weekdayPreferredShiftType` (опционально),
  - `weekendPreferredShiftType` (опционально),
  - `targetShiftsPerMonth`,
  - `wantsMoreShifts`.

Важный факт текущей реализации:
- `PUT /api/shifts/<id>` защищен `requireAdmin()` (см. `src/app/api/shifts/[id]/route.ts`) → обычный сотрудник получит `403`.
- `PUT /api/employees/<id>` защищен `requireAdmin()` (см. `src/app/api/employees/[id]/route.ts`) → обычный сотрудник не может редактировать карточку сотрудника целиком.
- Но `PUT /api/employee/preferences` доступен сотруднику (только свои предпочтения, whitelist полей + обновление cookie).

На практике сейчас:
- запрос смены и swap-заявки у сотрудника работают;
- “предпочтения” сотрудника работают;
- “отпустить напарника” требует доработки прав (или отдельного employee-доступного endpoint).

## 7) Веб: “Планирование смен” (менеджер) — как работает

### 7.1 Где лежит код
- Страница: `src/app/schedule/planning/page.tsx`
- Дашборд планов: `src/app/schedule/planning/components/PlanningDashboard.tsx`
- Страница плана: `src/app/schedule/planning/[id]/page.tsx`
- Редактор плана: `src/app/schedule/planning/[id]/components/PlanEditor.tsx`

### 7.2 Управление планами (PlanningDashboard)
`PlanningDashboard` показывает планы, сгруппированные по `plan.month`:
- загрузка: `getSchedulePlansData()` (server) → `initialPlans` (client state).

Действия:
- Создать план: `POST /api/schedule-plans`
- Клонировать: `POST /api/schedule-plans/<id>/clone` с `{ targetMonth: "YYYY-MM" }`
- Активировать: `PUT /api/schedule-plans/<id>` с `{ isActive: true }`
  - сервер при активации деактивирует другие планы этого месяца.
- Удалить: `DELETE /api/schedule-plans/<id>`
- Автозаполнить смены: `POST /api/schedule-plans/<id>/auto-fill` с `{ clearExisting: false }`

Права:
- `POST/PUT/DELETE /api/schedule-plans*` требуют `requireAdmin()`.
- `GET /api/schedule-plans` сейчас без auth (только чтение).

Важный факт:
- при создании плана `createdBy` сейчас хардкодится в UI как `emp_manager_admin` (`// TODO: Get from session`).

### 7.3 Редактор плана (PlanEditor): статусы дней
PlanEditor в режиме “Статусы сотрудников”:
- выбирается сотрудник;
- выбираются дни (клики по календарю);
- нажимается статус (`free`, `doesnt_want`, `vacation_sick`, `must_work`).

Запись идет в `data/employee-day-statuses/*.json` через:
- `POST /api/employee-day-statuses` (создание),
- `PUT /api/employee-day-statuses/<id>` (обновление).

Права:
- `POST/PUT/DELETE` требуют `requireAdmin()`.

Ограничение:
- UI не задает `shiftType/boxNumber` даже для `must_work`, поэтому статус “должен работать” влияет только на приоритет, а не на конкретный слот.

### 7.4 Редактор плана (PlanEditor): требования по дням (box1DayRequired и т.д.)
PlanEditor в режиме “Требования по дням”:
- для каждого дня есть 4 числовых поля:
  - `box1DayRequired`
  - `box1NightRequired`
  - `box2DayRequired`
  - `box2NightRequired`
- при изменении значения UI:
  - пересчитывает `requiredCount = сумма четырех полей`,
  - сохраняет план целиком через `PUT /api/schedule-plans/<planId>`.

Важно:
- авто-fill использует именно per-box поля (см. раздел 8).
- если per-box поля не заполнены, auto-fill использует fallback:
  - `requiredCount` интерпретируется как потребность на “день”, сначала в бокс 1 (до 2), затем в бокс 2 (до 2).

Практические правила UI:
- значения требований ограничены диапазоном `0..2` (в одном слоте максимум 2 человека);
- “Закрыто: 0” сохраняется как явная запись `DailyRequirement` с `requiredCount=0` (это важно, чтобы отличать “закрыто” от “пусто/не настроено”).

Погодный помощник (для модели “бокс 1 основной, бокс 2 резервный”):
- UI умеет загрузить прогноз для Вязников и подсказать дни, где достаточно 1 сотрудника (бокс 1 день).
- Endpoint: `GET /api/weather/forecast?month=YYYY-MM` (требует `requireAdmin()`).
- Правило “сильная погода”: дождь `>= 8 мм/сутки` или снег `>= 2 см/сутки` → рекомендуем `1`, иначе `2`.
- Эвристика “пик после осадков”: если после сильных осадков есть 3 дня подряд “солнышко”, рекомендуем “пик”: `3` (2 в бокс 1 день + 1 в бокс 2 день).
- Ограничение: прогноз ограничен ближайшими днями (даты без прогноза заполняются “Нормой: 2”).
- Подробно про погоду/журналы: `доки/09-ПОГОДА-И-ПАТТЕРНЫ.md`

### 7.5 Редактор плана (PlanEditor): “Сотрудники плана” (employeeConfigs)
PlanEditor в режиме “Сотрудники плана”:
- управляет списком сотрудников, которые участвуют в автозаполнении (плановый пул на этот месяц);
- хранит параметры автозаполнения в `plan.employeeConfigs[]`:
  - `targetShiftsCount` (цель смен на месяц),
  - `preferredShiftType` (day/night/any),
  - `wantsMoreShifts` (готовность брать сверх цели).

Права:
- сохранение идет через `PUT /api/schedule-plans/<planId>` и требует `requireAdmin()`.

Как это “склеивает” план и предпочтения:
- сотрудники задают свои предпочтения в `http://localhost:3000/employee/schedule` (см. `EmployeePreferences`).
- менеджер может нажать “Синхронизировать значения” в режиме “Сотрудники плана”, чтобы подтянуть:
  - цель смен/мес, тип смены, “хочу больше смен”
  из карточек сотрудников в настройки плана.
- предпочтения “будни/выходные” (`weekdayPreferredShiftType`/`weekendPreferredShiftType`) хранятся у сотрудника и учитываются auto-fill по дате автоматически (в план не копируются).

## 8) Алгоритм `auto-fill` (как работает реально)

### 8.1 Где лежит код
- Endpoint: `src/app/api/schedule-plans/[id]/auto-fill/route.ts`
- Данные: `data/schedule-plans/*.json`, `data/employee-day-statuses/*.json`, `data/employees/*.json`
- Результат: файлы `data/shifts/*.json` с `isAutoAssigned: true`

### 8.2 API и права
- `POST /api/schedule-plans/<id>/auto-fill`
  - body: `{ clearExisting: boolean }`
  - доступ: `requireAdmin()`

### 8.3 Псевдокод логики (смысловая версия)
1. Загрузить `plan` по id.
2. Загрузить `employees` и `dayStatuses`.
3. Пройти по всем дням месяца `plan.month`.
4. Для дня:
   - найти `dailyReq` по `date`;
   - если `dailyReq` нет или `requiredCount == 0` → пропустить день;
   - собрать `shiftRequirements` из per-box полей:
     - `(box=1,type=day,count=box1DayRequired)`
     - `(box=1,type=night,count=box1NightRequired)`
     - `(box=2,type=day,count=box2DayRequired)`
     - `(box=2,type=night,count=box2NightRequired)`
     - оставить только `count > 0`.
   - построить список доступных сотрудников (по конфигу плана), исключая:
     - `doesnt_want`, `vacation_sick`;
     - перегруженных (`assignedCount >= targetCount`), если `wantsMoreShifts=false`.
   - отсортировать по приоритету:
     1) `must_work` выше,
     2) меньшая переработка (assigned-target),
     3) `wantsMoreShifts=true` выше.
   - на каждый requirement:
     - выбрать сотрудников, стараясь совпасть с предпочтениями по типу смены:
       - если у сотрудника задано `weekdayPreferredShiftType` / `weekendPreferredShiftType`, они имеют приоритет по дате,
       - иначе используется `preferredShiftType` (day/night/any),
     - не назначать одного сотрудника дважды в один день (`assignedTodayEmployees`).
   - создать `Shift`(ы) и записать в `data/shifts`.

### 8.4 Важные ограничения текущей реализации
- Если в `data/shifts` уже есть дубли по слоту `(date, boxNumber, shiftType)`, auto-fill:
  - выберет один shift как “основной” (с большим числом сотрудников),
  - может дополнять его сотрудниками,
  - но **не удалит** остальные дубли (это нужно чистить отдельно).
- Требования по слотам и авто-fill ограничены диапазоном `0..2` (в одном слоте максимум 2 сотрудника по правилам системы).
- `must_work` влияет только на приоритет; не фиксирует смену на конкретный `shiftType/box`.

## 9) Telegram: как видит смены и как влияет на них

### 9.1 Чтение графика `/today /week /month`
- Worker: `telegram-bot/worker.mjs`
- Internal endpoint: `GET /api/telegram/internal/schedule?employeeId=...&range=today|week|month`
  - код: `src/app/api/telegram/internal/schedule/route.ts`

Как строится диапазон:
- today: `startOfDay(now)` .. `endOfDay(now)`
- week: today .. today+6
- month: `startOfMonth(now)` .. `endOfMonth(now)`

Фильтрация смен:
- берутся смены, где `shift.employeeIds.includes(employeeId)`,
- дата смены берется как `new Date(shift.date + "T00:00:00")`.

### 9.2 Telegram заявки (`/requests`, `➕ Запрос смены`)
Worker вызывает:
- `GET /api/telegram/internal/requests?employeeId=...` (`src/app/api/telegram/internal/requests/route.ts`)
  - входящие swap,
  - исходящие swap,
  - свои assignment запросы,
  - список ближайших смен,
  - список доступных сотрудников (для swap/giveaway).

Создание/действия:
- Assignment:
  - `POST /api/telegram/internal/shift-assignment/create`
  - `POST /api/telegram/internal/shift-assignment/cancel`
- Swap/giveaway:
  - `POST /api/telegram/internal/shift-swap/create`
  - `POST /api/telegram/internal/shift-swap/respond`

Важно: internal endpoints вызывают те же сервисы `shift-*-service.ts`, что и веб API, поэтому правила должны совпадать.

### 9.3 Уведомления по сменам и заявкам (snapshot/diff)
Механизм:
1. Worker периодически вызывает `GET /api/telegram/internal/snapshot?employeeId=...&cursor=...`.
2. Сервер собирает “срез” (shifts, requests, transactions, washes).
3. Если курсор совпал с прошлым — строит events через `src/services/notification-diff-service.ts`.

Для смен используется `signature`, которая включает:
- `date`, `boxNumber`, `shiftType`, `startTime`, `endTime`,
- отсортированные `employeeIds`,
- `releasedEmployeeId`.

Это значит: изменение состава смены или отпуск напарника трактуется как “shift_updated” и может отправить уведомление.

## 10) Операционные сценарии (как действовать)

### 10.1 “Я вышел на работу, а меня нет в графике”
Самый быстрый стандартный путь (сотрудник сам):
1. Telegram: `➕ Запрос смены` или команда `/requests` → создать request на нужную дату/тип/бокс.
2. Менеджер в веб: `http://localhost:3000/schedule` → “Запросы на смены” → “Назначить”.
3. Сотрудник получает уведомление “Новая смена”.
4. Проверка:
   - в TG `/today`;
   - или в веб `http://localhost:3000/employee/schedule`.

Альтернатива (менеджер вручную):
1. Веб: `http://localhost:3000/schedule`
2. Клик по нужной дате в строке сотрудника → выбрать тип смены + бокс + сотрудников → “Сохранить”.

### 10.2 `/wash` не запускается (или бот пишет “нет смены на сегодня”)
Проверить:
1. Есть ли смена на **сегодняшнюю дату** в `data/shifts/*.json` у этого сотрудника.
2. Что сотрудник не “admin” (admin тоже может работать, но в некоторых потоках employee UX предполагает обычную роль).
3. Если смены нет — создать/принять assignment запрос (см. 10.1).

## 11) Known issues (факты текущей реализации)

Финальный список проблем, которые важно знать перед доработками:
- Если per-box поля `box*Required` не заполнены, `auto-fill` использует fallback:
  - `requiredCount` интерпретируется как потребность на “день”, сначала в бокс 1 (до 2), затем в бокс 2 (до 2).
- `must_work` в `EmployeeDayStatusEntry` сейчас:
  - в UI не задает `shiftType/boxNumber`;
  - в auto-fill не принуждает к конкретному слоту.
- `/api/shifts` не валидирует:
  - уникальность слота `(date, boxNumber, shiftType)`,
  - ссылочную целостность `employeeIds`,
  - ограничения по 1..2 сотрудника на смену.
- Принятие assignment request (`resolveAssignmentRequest`):
  - не проверяет конфликт занятости сотрудника с другими сменами на дату;
  - добавляет сотрудника в “первую найденную смену” слота (если слоты продублированы).
- В `ScheduleCalendar` при клике по ячейке в редактирование передается только `empShifts[0]` (если на дату несколько смен, редактируется “первая попавшаяся”).
- Поле `managerApproved` передается UI в swap-решении, но сервером не используется.
- “Отпустить напарника” в employee UI сейчас вызывает admin-only API (`403` для обычного сотрудника) и требует доработки прав/эндпойнтов.
- Флаг `employee.canSwapShifts=false` сейчас ограничивает только UI, но не серверную логику создания swap-заявок.

## 12) Чек-лист регрессии (ручная проверка)

### Менеджер: ручные смены
1. Зайти admin → `http://localhost:3000/schedule`.
2. Назначить смену (дата, бокс, день/ночь, 1–2 сотрудника).
3. Проверить:
   - запись появилась в `data/shifts/*.json`,
   - сотрудник видит смену в `http://localhost:3000/employee/schedule`.

### Сотрудник: запрос смены
1. Сотрудник → `http://localhost:3000/employee/schedule` → “Запросить смену”.
2. Менеджер → `http://localhost:3000/schedule` → “Запросы на смены” → “Назначить”.
3. Проверить TG:
   - `/today` показывает новую смену,
   - приходит уведомление `Новая смена` (если worker запущен и snapshot синхронизирован).

### Планирование: требования + auto-fill
1. Менеджер → `http://localhost:3000/schedule/planning` → создать план на месяц.
2. Открыть план → режим “Требования по дням”.
3. Для 2–3 дат поставить per-box требования (например `box1DayRequired=1`, `box2DayRequired=1`).
4. Запустить “Автозаполнить” → проверить:
   - появились новые файлы `data/shifts/*.json` с `isAutoAssigned=true`,
   - смены отображаются в `/schedule`.

### Swap/giveaway
1. У 2 сотрудников есть смены в будущем.
2. Сотрудник А создает giveaway/swap.
3. Сотрудник B принимает (или менеджер принимает).
4. Проверить:
   - обновились `employeeIds` у смены(смен),
   - пришло уведомление в TG (если был синхронизированный snapshot cursor).
